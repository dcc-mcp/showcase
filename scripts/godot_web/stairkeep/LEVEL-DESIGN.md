# 阶塔：三层可玩切片

「阶塔」是临时名，可改名；英文工程代号 Stairkeep。目标是 8–15 分钟的一局经典确定性魔塔，用 2.5D 等距画面呈现四向逻辑网格。这里是关卡与数值设计，不是 UI 或美术验收结果。

机器可读的唯一数值来源为 [levels.json](levels.json)。坐标为零基 `[x,y]`，左上是 `[0,0]`；地形 `#` 是墙，`.` 是可行走地面。对象由独立稳定 ID 表示，存档必须按 ID 保留已拾取、已击败、已开门与商店购买次数。

## 规则

初始角色：260 生命、24 攻击、8 防御、0 金币、0 黄钥匙、0 蓝钥匙。生命没有上限，符合魔塔中资源累计的用法。攻击、敌人和拾取都没有随机数。

预览与实际战斗必须调用同一个函数：

```text
单次伤害 = hero.atk - enemy.def
若单次伤害 <= 0：攻击不足，不可胜，不执行战斗。
击杀所需攻击数 = ceil(enemy.hp / 单次伤害)
敌人回击数 = 击杀所需攻击数 - 1   # 主角先手
预计损失 = 敌人回击数 * max(0, enemy.atk - hero.def)
可胜 = hero.hp > 预计损失
```

主角生命恰好等于预计损失也不可胜；不可胜交互不改变生命、金币、对象状态或位置。胜利只扣一次预览损失、奖励一次金币并清除敌人。攻击不能消耗格外的移动回合或隐含伤害。

门第一次成功打开时扣一把对应钥匙，记录为已打开；往返已开门不再扣钥匙。没有钥匙时不移动、不扣其他资源。钥匙、药水、宝石、金币均只拾取一次。商店也是固定数据，扣款与属性增加必须原子完成，购买次数随存档恢复。

楼梯双向链接，并保留每层所有状态。进入目标层时落在返回楼梯所在格；这次转层不能递归触发返回楼梯，需新的输入离开再进入或显式交互。鼠标点相邻格、点击目标后逐格路径移动、方向键/WASD 都遵守四向邻接；等距画面不引入对角逻辑移动。

## 空间结构

三层共享同一个紧凑、易读的 9×9 底图，使用不同的材质、光色、墙体构件和布景。每个小室只有一个入口，锁门和敌人都不能从旁绕过；中央横廊保持视线清晰。

```text
#########
#...#...#
#...#...#
##.###.##
#.......#
#.#####.#
#...#...#
#...#...#
#########
```

左下是抵达区，`[1,5]` 是出口窄口；右下是可选资源室，`[7,5]` 是入口；左上是可选奖励室，`[2,3]` 是入口；右上是楼梯或塔心，`[6,3]` 是入口。这些入口坐标都是实际可行走格，不是装饰门。

## 第一层：苔门层

视觉方向：石青与苔绿的旧地牢，温黄钥匙和门环；暖光标记可以抵达的物资，楼梯使用同一套轮廓图标。玩家从 `[1,7]` 抵达，苔团是低代价的第一次战斗。

| ID | 坐标 | 内容 |
|---|---|---|
| f1_key_start | 2,7 | 黄钥匙 ×1 |
| f1_moss | 1,5 | 苔团：35 HP / 13 ATK / 4 DEF，8 金币 |
| f1_door_armory | 2,3 | 黄门，攻房入口 |
| f1_atk | 1,1 | 攻击 +3 |
| f1_potion | 3,1 | 生命 +60 |
| f1_cinder | 7,5 | 余烬妖：50 HP / 18 ATK / 8 DEF，12 金币 |
| f1_key_spare | 7,7 | 黄钥匙 ×1 |
| f1_door_stairs | 6,3 | 黄门，楼梯室入口 |
| f1_up | 7,1 | 上楼 → 第二层 1,7 |

第一把黄钥匙可直接开楼梯，也可先开攻房。先开攻房后仍可用增强后的攻击击败右下余烬妖，取第二把钥匙继续上楼，不会因支线选择锁死。先上楼的玩家可之后原路返回补取资源；每层状态保留。

商店固定选择：20 金币磨刃，攻击 +6，限 1 次；20 金币铸甲，防御 +4，限 1 次；15 金币补给，生命 +120，限 2 次。所有价格、收益、次数上限显示在购买前，货币不足按钮不可执行。

石甲守卫的 27 防御构成明确门槛：攻击 27 时不可胜；购买磨刃变成 33 攻击后，若防御仍是 8，则预览损失正好 80，实扣也应为 80。第一层没拿攻宝石也可通过磨刃成为 30 攻击，不过守卫战斗损失更高。

蓝钥匙选择同样可恢复：可直接保留给第三层主门，也可先换护甲与金币；右下可选战斗后能补第二把蓝钥匙。先取得护甲降低右下战斗和后续主线损失；省略蓝库和右下战斗则需要把金币用于生命补给。

## 数值验证

使用 Python 3.12 标准库执行同一整数公式，检查了 34 个对象 ID 唯一、每层对象坐标不重叠、所有对象与楼梯目标都位于可行走格。BFS 另外通过了 9 个单口门/敌人拓扑检查：阻挡入口确实无法从旁抵达奖励，封印哨兵占据其格时仍可抵达 Boss。下面四条路线都通过了钥匙计数、商店支付与购买上限检查。完整事件账本与每步状态在 `levels.json` 的 `validated_routes`。

| 路线 | 商店购买 | 塔顶选择 | 通关剩余 HP | 最终 ATK / DEF | 剩余金币 |
|---|---|---|---:|---|---:|
| resource_blade：取第一层攻房、第二层蓝库与备用蓝钥匙 | 磨刃、铸甲 | 锋刃室 | 49 | 38 / 16 | 177 |
| resource_supply：同上 | 磨刃、铸甲 | 补给室 | 78 | 33 / 17 | 157 |
| skip_f1_armory：第一层直接上楼，第二层补足护甲与备用钥匙 | 磨刃、铸甲、补给 ×1 | 锋刃室 | 20 | 35 / 16 | 150 |
| save_blue_skip_vault：保留蓝钥匙，省略第二层蓝库与碎骨弓手 | 磨刃、铸甲、补给 ×1 | 锋刃室 | 85 | 38 / 12 | 120 |

资源丰收路线的塔心战预览为 140，生命 189 → 49；补给选择的塔心战预览为 171，生命 249 → 78。不同钥匙和购买路线会改变攻击回合数、生命余量、金币与必经敌人，不能用固定剧情扣血替代计算。

这些是数值与数据完整性验证，不代表 Godot 运行、输入、存档或 Web 浏览器已经验收。

Godot 逐步回放对照时发现设计账本的商店步骤曾浅拷贝钥匙字典，导致 7 个中间快照被后续开门污染为蓝钥匙 0。现已对每个事件重建独立深拷贝快照：这些商店步骤的真实蓝钥匙为 1，四条路线最终资源、战斗损失、预算与通关结论均未改变。实际规则与严格逐步断言无需因此调整。

## 交付前验收场景

1. 拿第一层黄钥匙，开攻房黄门，记录钥匙 1 → 0；重复往返该门仍为 0。打余烬妖取第二把后可打开楼梯门。
2. 第一层取攻击宝石、开门、清除一个敌人，上二层再回一层；对象清除和开门状态保持，没取的物品仍在。
3. 用 260 HP / 33 ATK / 8 DEF 对石甲守卫，预览 80；执行战斗后生命 180，金币增加 25，仅发生一次。
4. 用 80 HP / 33 ATK / 8 DEF 对同敌人，预览 80 且不可胜；战斗输入无副作用。用 27 ATK 对它提示攻击不足，不显示可胜。
5. 对封印哨兵显示不可胜和攻击不足；玩家可返回选择其他相邻通路，不能扣血后继续。
6. 第二层先花蓝钥匙开蓝库，再打碎骨弓手取备用蓝钥匙；第三层主门可开。另一局保留蓝钥匙跳过两支线，买生命后同样能赢。
7. 第一层直接上楼时可回头补资源；使用 `skip_f1_armory` 路线也能通关。第三层黄钥匙只能开两个支线中的一个，另一个留锁。
8. 在第二层打开蓝库并购物后存档，退出重开再读取；角色、楼层位置、钥匙、已开门、已清敌人、物品与商店次数完全恢复。加载不能重新发奖励。
9. 重置新局清除本地进度并恢复初始角色、全部对象、商店次数和第一层出生点；重置操作本身有明确 UI 含义。
10. 经 HTTP 加载单线程 Web 导出，在实际浏览器完成输入、至少一场预览与实扣对比、双向楼层、存读档和通关。未完成项在回执中单列。
