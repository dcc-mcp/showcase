# 阶塔：21 层战役设计草案

状态：**可评审设计，尚未实现或验收**。「阶塔」是可改名的临时名称。

本设计只新增此文档，不扩充或覆盖现有三层数据。当前工作优先完成三层切片的 Godot、HTTP Web 实际浏览器验收；浏览器窗口权限仍处于 blocked，规划文档、headless 规则验证和实际浏览器验收分别记录，不能互相替代。

现有三层保留为独立内容 `stairkeep-slice-3/v1`。未来 21 层使用独立 `stairkeep-campaign-21/v1` 内容 ID、数据、存档槽与验收回执。若复用当前前三层机制与几何，应复制进新内容版本；第三层从切片通关改为章节解锁也是需要评审的行为变更，不能顺手改变已验切片。

## 战役结构与游玩时长目标

21 层分为七组，每组三层形成「观察与准备 → 资源取舍 → 兑现前两层的投资」节奏。怪物位置、类型、数值、掉落、钥匙颜色、门和商店库存均由关卡数据固定。变体只做下文规定的镜像和首层安全出生选择，不重排怪物或随机改数值。

首轮完整通关 **2–4 小时是设计目标，尚无人工时长证据**。初步预算为七组各 15–25 分钟，加 15–45 分钟跨层回访、预览与商店规划，共 120–220 分钟。不得以增加走空路、等待、强制重复战斗或阅读阻塞填满时长；如果人工试玩明显短于目标，应增加有信息支撑的资源决策或缩小宣传目标，再评审后修改内容。

使用现有合许可模板和素材作为组件，不复制来源不明或原关卡权利不清的魔塔布局。新布局、数值和怪位由本项目自行设计；每种外部素材继续记录具体来源、版本、许可、归属与文件哈希。未取得许可的内容不能因只做镜像就进入项目。

## 固定布局与受控镜像规范

### 原始内容与对象身份

数据保留一份 canonical 关卡；运行时只生成独立变体副本，不原地改 canonical 数据。每层有稳定 `floor.id`、矩形 `grid`、`spawn`、`objects`；对象 ID 跨层唯一，不含坐标语义。所有跨层目标使用 `target.floor` 和 `target.pos`，可选带 `target.object_id` 作为一致性校验。

在变体中，敌人 ID、类型、HP/ATK/DEF、奖励、门钥匙颜色、拾取数量、商店 offer 与库存均不改变。楼梯的 `up/down` 是楼层语义，镜像不会颠倒上下楼；面朝方向或绘制朝向若存在则同步反射，不影响属性和战斗。任何未来依赖朝向的伤害机制都必须重新证明下文的同构关系。

### 可复现 PRNG 与变体序列

规范版本命名为 `stairkeep-variant/xorshift32-hv-v1`。不使用 Godot 的隐式默认 RNG、系统时间、对象 hash、未排序字典枚举或平台相关随机数来生成布局。

1. 用户/测试输入 seed 为无符号 32 位，持久化为八位十六进制字符串。`00000000` 规范化成 `6d2b79f5`，UI 与回执显示规范化后的值，不能让零状态进入生成器。
2. `next32(s)` 使用逻辑右移与每步 32 位截断：

   ```text
   s = (s XOR ((s << 13) AND 0xffffffff)) AND 0xffffffff
   s = (s XOR (s >> 17)) AND 0xffffffff
   s = (s XOR ((s << 5) AND 0xffffffff)) AND 0xffffffff
   return s
   ```

3. 新战役的 `root_seed = campaign_seed = sequence_state`，`attempt_index = 0`。生成布局使用局部变量 `variant_state = campaign_seed`，不能消耗 `sequence_state`。
4. `floor.id` 为连续整数 1–21，按数值升序，对 21 层分别取两次 `next32`；第一次结果的最低位决定 `mirror_h`，第二次最低位决定 `mirror_v`。第 1–42 次抽取只用于这 42 个布尔值。第 43 次结果仅用于首层出生候选索引。固定 draw 次序写入版本规范；新增装饰随机数必须使用独立 stream，不能插入这 43 次抽取。
5. 「重开同一 seed」不改变 `campaign_seed`、`attempt_index` 或 `sequence_state`；清空本局经济与地图状态后重新生成同一变体。「新变体重生」明确确认后执行一次 `sequence_state = next32(sequence_state)`，`attempt_index += 1`，`campaign_seed = sequence_state`，再从头生成新局。
6. 战斗失败/资源败局本身不自动推进序列。失败弹窗重复显示、加载失败前存档、应用重开都不能偷偷取下一个 seed。失败事件带稳定 ID，计数只记录一次；种子序列变化来自用户选定的重生操作，而非帧数或弹窗次数。

同一内容哈希、规范版本、`campaign_seed`、首次出生规则和输入决策序列必须得到同一对象位置和资源结果。PRNG 只提供可复现变体，不承担安全用途，也不声称所有镜像组合均匀分布。

供实现跨语言比对的黄金向量，已用 Python 标准库按上述位运算计算；这不是 Godot 实现通过记录。`spawn_index` 的候选数固定为 4：

| campaign_seed | 第1–6次输出（十六进制） | 第43次输出 | spawn_index | 新变体的下一 seed |
|---|---|---|---:|---|
| 00000001 | 00042021, 04080601, 9dcca8c5, 1255994f, 8ef917d1, 2c6f5bd0 | 48213943 | 3 | 00042021 |
| 013528a1（十进制20261025） | 200a0c91, 529b97fd, 2ce0de2f, d381921d, d98a1d7c, de9fddae | e6af7b5f | 3 | 200a0c91 |
| 6d2b79f5（零输入规范化） | 40aec71f, 91e00c19, 9c0fe128, 6570f69d, 0fce02cc, 3d6b45e7 | 12790098 | 0 | 40aec71f |

### 全图坐标反射

对源层 `f` 的宽 `W_f`、高 `H_f` 定义：

```text
T_f([x,y]) = [mirror_h ? W_f - 1 - x : x,
              mirror_v ? H_f - 1 - y : y]
```

执行顺序与约束：

1. 校验 canonical 全图矩形、边界、对象 ID 唯一、对象坐标和所有目标可走，再生成副本。
2. 对每个 canonical 格 `[x,y]`，赋值 `variant.grid[T_f(x,y)] = canonical.grid[x,y]`；墙体、可走地面及任何真正改变规则的 tile 标记都同步。
3. 本层所有 `object.pos`、本层普通 `spawn`、标记点、可交互区域和地面触发格都用 `T_f`。若对象或区域占多格，则逐格反射并重新规范化边界，不只反射一个视觉中心。
4. 位于层 `f` 的楼梯对象位置用 `T_f`；它的 `target.pos` 用**目的层** `T_target_floor`。不能误用出发层尺寸或镜像标志。`target.floor`、稳定对象 ID 保留不变。双向楼梯检查应核对变体目标仍指向对应返回楼梯，不会递归自动弹回。
5. 方向向量 `[dx,dy]` 对应变成 `[mirror_h ? -dx : dx, mirror_v ? -dy : dy]`，只用于方向相关呈现和边界信息。键盘继续控制当前屏幕逻辑方向；鼠标寻路针对变体网格重新求路，不能沿用 canonical 的旧路径缓存。
6. 检查每种门颜色、钥匙数量、怪物类型与数量、掉落总量、HP/ATK/DEF 宝石总量、金币和商店库存完全守恒。重建邻接图后验证 `T_f` 是可走图同构；本层所有楼梯连接纳入全战役有向图校验。

反射两次必须还原原坐标，h 与 v 交换执行次序结果相同。UI 小地图、目标高亮、范围预览、寻路、存档和测试都读取同一变体数据；禁止画面反射了但碰撞/交互仍使用旧坐标。

跨尺寸目标测试例：出发层为 9×9、h=true/v=false，其楼梯 `[7,1]` 变为 `[1,1]`；目的层为 11×13、h=false/v=true，原 `target.pos=[1,7]` 必须变为 `[1,5]`，不是按出发层反射得到的 `[7,7]`。楼梯仍向原目的楼层转移。

### 出生候选只作用于第一层

21 层作者在 canonical 第一层显式列出 `safe_start_candidates`，按 `(y,x)` 排序。候选必须同时满足：可走、没有任何对象、不是楼梯或触发格、四邻无敌人，并与 canonical 第一层默认出生点位于同一个初始**空格**连通分量。计算该分量时，所有拾取、门、敌人、商店和楼梯均视为不可穿过，因而从候选回到默认出生点不会自动拾物、扣资源或转层。

索引为第 43 次 PRNG 结果 `% candidate_count`，选取 canonical 候选后再应用 `T_1`，得到 `resolved_start`。候选为空时内容校验失败，不能扩大范围随机挑怪物旁的格子。当前三层首层可供未来复核的候选按 `(y,x)` 排序为 `[2,6]`、`[3,6]`、`[1,7]`、`[3,7]`；这只是原型候选，不自动授权修改三层出生行为。

其他 20 层没有随机出生选择：转层严格使用已同步的 `target.pos`。死亡后重生也只从新局第一层 `resolved_start` 开始，不能把败局角色位置随机放到高层以绕过锁门。

## 死亡、资源败局与受控恢复

当前切片禁止执行致死战斗，因此「资源耗尽、无法推进」与 HP 已归零的死亡是两个不同原因。未来若允许确认后执行致死战斗，必须版本化该规则并保存失败原因；本设计不通过改变当前不可胜交互来引入死亡。

失败判定分为四种，不能混写：

| 状态 | 可以说明什么 | 行为 |
|---|---|---|
| 当前敌人不可胜 | 攻击不足，或 HP 不大于这场战斗损失 | 显示具体原因，不改资源；可返回其他通路。 |
| `resource_exhausted` | 完整导航 BFS 已检查全部可达层，找不到任何可拾取资源、可胜敌、可开门或可支付且有库存的商店动作，且未通关 | 明确说明当前状态已无推进动作，提供可用恢复操作。 |
| `loss_proven` | 下文精确状态求解已穷尽所有可能后续资源决策，证明不存在通关后缀 | 可提前提示败局证据；仍允许查看地图与复盘。 |
| `unknown` | 求解时间/内存预算耗尽，或规则不在求解器覆盖范围 | 只能说明未能判定，不能把它标作必败或安全。 |

据当前三层协调回执，10,000 次多 policy 测试中的 randomized 子集出现 **20 / 2,000** 个 `dead_end`（该子集为 1.0%）。常见序列是低攻击先挑战高代价敌，提前用完两次治疗库存，最后 Boss 预计损失 140、现有 HP 99、金币 97，但已无可用药水库存和其他可达资源。这是明确可复现的**资源耗尽可选败局**，不能因金币还有 97 就说商店一定能救回，也不能把它改写为随机数或引擎故障。它不是 21 层结果、人工失败率或所有玩家政策的失败率；原始 `dead_end` 统计与失败轨迹必须保留。

败局面板至少显示：当前 HP、阻挡目标的预览损失、差额、相关商店剩余库存、最近关键花费、seed/变体和回档点。示例应解释「需承受 140，当前 99；治疗库存 0」，而不是只有「失败」。若完整 BFS 证实无动作，不能继续用「还有别的路」作无依据提示。

允许的恢复路径必须明确且完整恢复状态：

- **读取已有存档/章节入口快照**：恢复该快照的全部经济、对象、库存、位置和相同变体，不能只恢复 HP 或撤回某一次购买。章节入口快照可能已包含较差的历史选择，不自动保证可赢；没有可赢证明时仍提供从整局起点重开。
- **重开同一 seed**：恢复初始角色、所有对象、门、商店和第一层出生点；保留序列索引，不洗掉可复现实例。
- **新变体重生**：按上一节准确推进一次 seed 序列，清空整局资源状态，从新变体的第一层安全出生点开始。不能保留旧层已清状态、旧钥匙或库存进入新地图。

**是否添加救济仍是平衡决策，不在本设计中暗改。** 可评审选择包括保留经典败局并强化回档说明，或增加公开、有限、定价明确的救济机制；后者需要新的内容版本、可见库存和预算，并重新跑可赢与败局验证。不得偷偷发金币、按差额补血、加载时补商店 stock、挪走阻挡敌人，或从测试结果中删除失败轨迹来掩盖风险。

## Save v2 与复现包

现有 Save v1 不作静默升级成 21 层。v2 使用单独存档槽；读到 v1 时允许继续旧三层或开启新战役，不凭空补充中段角色资源。迁移/读取失败不能覆盖原字节。

v2 必存字段至少包括：

```text
schema_version = 2
content_id, canonical_content_sha256, rules_version, rules_sha256
variant_spec = stairkeep-variant/xorshift32-hv-v1
root_seed, campaign_seed, sequence_state      # eight-character hex strings
attempt_index, variant_draw_count = 43
floor_mirrors[stable_floor_id] = {h, v}
resolved_start, transformed_content_sha256
state = {
  floor, pos, hp, atk, def, gold, keys_by_color,
  cleared_object_ids, purchase_counts_by_shop_and_offer,
  story_flags, won, failed, failure_reason, failure_event_id
}
decision_index, decision_log_hash, checkpoint_id
checkpoints[] = {same version/seed binding + complete state + decision index}
```

显式保存镜像表用于诊断，但加载时必须从 seed 和规范重生成并逐项核对，不能接受任意篡改的镜像表；`transformed_content_sha256` 对 UTF-8 的规范 JSON 计算：字典键排序，层按整数 ID、对象和清除列表按稳定 ID 排序，整数不写成浮点，无时间戳/宿主路径，禁止不确定顺序。资源值都是整数；校验非负、合理内容上界、合法对象 ID、库存次数上限、目标楼层/坐标可走、钥匙颜色存在、清除列表无重复、胜负标志一致。内容、规则或规范哈希不匹配时停止载入并给出可理解说明，不在不知情时重新生成另一张图。

保存过程使用完整快照的原子替换方案；Web 持久化还须等实际存储完成后才显示「已保存」，失败时保留旧存档并显示未保存。验收需要经 HTTP 的真实浏览器关页重开、读档、重开同 seed 和新变体恢复结果，不能只测内存中的序列化往返。

复现包记录原始 seed、当前 seed、序列索引、内容/规则哈希、引擎版本、完整决策事件 ID、每步资源账本、失败原因和最终状态。逐步账本必须深拷贝嵌套 `keys` 与购买表，避免本轮曾出现的商店中间钥匙快照被后续开门修改的问题。

## 资源求解、dominance 与每 seed 可赢证明

### 精确状态与决策边界

求解器必须使用正式游戏规则 API 执行移动、楼梯、拾取、开门、购物和战斗，不复制一套近似战斗公式。普通移动和楼梯若不改变资源，可用跨层 BFS 压缩到当前可达空格连通分量；边界动作仍必须由正式规则执行并重新计算连通分量。

状态包括：内容/规则/变体绑定、位置连通分量、HP/ATK/DEF、金币、每种钥匙、已拾/已清/已开对象集合、每个商店每个 offer 的购买次数、剧情旗标和胜负状态。不能只按楼层或 HP 去重，也不能把有剩余治疗库存和已卖光的商店视为同一状态。

为保持搜索有限，所有奖励、怪物、门、拾取和商店库存有限；不允许无限免费治疗、无上限金币循环或出售回购套利。当前无时间伤害、无导航消耗、无重生怪物和无隐藏随机数的前提必须写进版本。未来加入陷阱、再生或回合计时后，移动压缩和状态定义必须重做。

### 保守 dominance 规则

只在以下离散签名**完全相同**时比较资源：相同内容/规则/seed、相同已清/已拾/已开集合、相同购买次数和剧情旗标、相同当前可达空格连通分量。

若 A 的 `HP、ATK、DEF、gold` 及每种钥匙均不小于 B，且至少一项更大，则 A 可支配 B，B 可从搜索前沿剔除。这依赖现有战斗/商店规则对这些资源单调：更高属性不会触发更强敌人，更高金币不会提高价格，也没有携带惩罚。任何违反此前提的新机制都必须关闭对应 dominance 优化。

不要跨不同已清集合做「超集更好」剪枝：被清掉的怪物可能原本带金币，门后的钥匙可能未取；同样不要忽略商店库存差异。若更强状态 A 已由另一条历史实际可达，则它足以代表 B 的未来搜索；恢复失败状态时仍恢复玩家原状态，求解器不能把玩家升级成 A。

### 可赢证明与未知结果

发布前先对 canonical 21 层完成精确求解，生成至少一条正式规则可重放的通关证人；另提供攻击偏好、防御偏好或保留金币等至少两条人工可解释资源路线。证人包括稳定事件 ID、实际四向移动/楼梯路径、购买序列和每步资源，不只有最终数值。

镜像是图同构，属性/资源不变；首层候选与默认出生在同一初始空格分量，因此 canonical 证人可通过坐标变换得到同资源结果。每个可发布 seed 仍需在其实际变体上从 `resolved_start` 重放证人，核对对象身份、楼梯、门颜色、库存与最终胜利，并保存 seed 对应通过回执。运行时允许任意用户 seed 时，须先对该变体做同样的隔离状态重放校验；失败应拒绝这份变体并报告原因，不能悄悄换 seed。若只实现了离线校验，则产品只能提供已校验 seed 列表。

这保证「每个接受的 seed 至少存在可赢路线」，不保证任意消费顺序都能赢。对任意中途状态，精确求解返回：`witness_found`（有可重放通关后缀）、`unsatisfiable`（全部状态穷尽且没有后缀），或 `unknown_budget_exhausted`。超时不等于败局证明。报告求解耗时、状态数、dominance 剪枝数、规则/内容哈希和证人，不能只给绿色通过标签。

至少 10,000 次多 policy 运行用于补充压力探索，记录每种政策各自分母、seed、独立决策序列、dead-end/通关和预算分布。它有助于发现坏体验和策略风险，不能替代存在性证明或证明所有玩家都不会软锁。RL 可作为额外探索政策或路线建议，模型奖励、成功率和训练收敛不能成为唯一安全保证。

## 人工测时与验收门槛

先在浏览器权限正常且不与其他宿主任务争用的窗口完成三层验收，再推进 21 层实现。当前没有启动宿主、浏览器或执行部署。

21 层首轮测试建议覆盖至少 6 位首次接触本战役的玩家和 2 位熟悉确定性魔塔的玩家，实际数量不足时如实报告。记录首个可控输入到胜利/失败的墙钟时间；同时独立记录活跃时间、暂停、离开页面、阅读预览、跨层回访和恢复尝试。报告中位数、范围、各组耗时、完成比例和未完成原因，不能仅挑最长一局作为「数小时」。熟悉机制与首次游玩分别统计，重复 seed 的学习效应单列。

设计目标只有在精确版本上完成真实输入与全流程人工测时后才可写成观测结论；2–4 小时目标未达时，维持「目标」措辞。若访问被拒或仍 blocked，报告具体未验项，不能通过另一路桌面或自动点击绕过。

实现后的独立验收矩阵：

| 类别 | 必须留下的证据 |
|---|---|
| 关卡与许可 | 21 张原创通路/对象表、素材来源与许可、固定怪位及资源预算；三层原内容哈希不变。 |
| 变体 | h/v/双镜像/无镜像坐标单元测试、不同尺寸目的层 target 测试、图同构与资源守恒；首层全部出生候选通过检查。 |
| seed/重生 | 固定 seed 黄金向量；同 seed 重开完全相同；新变体只推进一次序列；保存重开后继续得到同一下一 seed。 |
| 规则与证人 | 每个接受 seed 的正式规则证人重放、预览=实扣、钥匙一次消耗、跨层对象与商店状态、最终胜利触发。 |
| 败局 | 重放当前 HP99/金币97/治疗售罄/Boss损失140 反例；信息解释正确，不暗增资源；同 seed 重开、完整回档、新变体恢复各自通过。 |
| 求解 | 明确 witness/unsatisfiable/unknown；商店 stock 与购买顺序纳入状态；dominance 关闭后小图结果一致。 |
| Save v2 | 原子保存失败保护、v1保留、内容不匹配拒绝、嵌套快照不污染；HTTP真实浏览器关闭重开后恢复与序列一致。 |
| 多 policy | 至少10k实际运行及每policy分母、复现轨迹和失败分布；不把随机策略失败率当人工失败率。 |
| 实际体验 | 三层与21层分别保留浏览器输入证据；人工全战役测时、章节节奏、可读性和回档体验；未完成项标 not-tested/blocked。 |

完成设计、headless 测试或草稿 PR 均不代表已满足上述门槛；合并、发布和上线仍是独立动作。
