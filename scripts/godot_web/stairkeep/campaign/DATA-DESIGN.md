# 21 层固定战役数据

此目录是独立规则/数据原型，不修改已冻结的三层切片。临时名「阶塔」可改。这里的通关数字来自构建时资源预算；正式 Godot 回放另留精确哈希绑定的报告，均不能代表浏览器或人工游玩通过。

## 固定内容与构建

`tools/build_campaign.py` 只使用 Python 标准库，展开作者固定选择的房间边集合、坐标角色和整数数值曲线。它不联网、不下载、不安装，也不在运行时摆怪。`data/levels21.json` 保留完整显式 canonical 网格、对象坐标、敌人属性和商店库存，运行时可以直接加载而不执行构建器。

```text
python tools/build_campaign.py
python tools/build_campaign.py --check
godot --headless --path . --script res://tests/replay_witnesses.gd -- --output=<absolute-report-path.json>
```

`--check` 重新生成并逐字节比较现有 JSON，不写输出。构建预算使用主角先手的整数公式；Godot 测试则直接使用冻结的 `scripts/base_rules.gd` 的正式 `combat/move/use_stairs/buy/interact`，不会将 Python 预算公式当作实际引擎验收。

21 层都是原创建构，未复制任何旧魔塔关卡。九个 3×3 小室嵌在 13×13 网格中，每室之间只有一格宽的固定连接；攻击房、护甲房与藏箱房处于单口支线。`CURATION` 固定选择 21 个不同的带房间编号/空间嵌入的边集合。忽略坐标后共有八种无标号树结构，因此不能将此宣传为 21 种完全不同的抽象图结构；不同楼层的空间位置、主路长度、支线归属和经济节奏均可在 `topology` 中审查。

## 七组节奏

| 组 / 层 | 固定差异 | 经济与可见取舍 |
|---|---|---|
| 苔门 1–3 | 短主路、分叉选择、星形汇合；首层石甲门卫有 28 防御。 | 首层锻炉攻击 +4 改变低攻击路线的可胜性；黄钥匙用于攻击或护甲房。 |
| 雨井 4–6 | 三种不同的短主路与外侧藏箱结构。 | 第4层蓝钥匙保留至第6层；可选战斗用生命换金币和一瓶固定药水。 |
| 铜炉 7–9 | 前两层七室长主路；三层攻击房都有第二道守卫和内部单口隔墙。 | 攻击投资要先支付守卫损失；护甲路线绕开这笔代价。 |
| 镜藏 10–12 | 星形、侧廊和长回访通路组合。 | 10层锻炉可后续回访；节制见证路线专门省略这一次铸甲，最后生命余量更紧。 |
| 霜桥 13–15 | 长桥与分叉窄路；三层攻击房有固定守卫。 | 重复回击放大护甲收益，攻击路线用高单击伤害抵消回击次数。 |
| 余烬 16–18 | 先分叉、再长主路、再汇合。 | 本组完整锻炉后置到18层，16–17层不能提前购买本组属性。 |
| 星冠 19–21 | 最后回廊与分叉；封印哨兵在21层可避开的角格。 | 19层只有两次生命补给；仅21层塔心监守触发战役胜利。 |

楼梯有40个，全部双向并带目标对象 ID 校验。蓝钥匙7把与章节蓝门7个对应，分别在每组第一层与第三层；黄钥匙共21把，竞争42扇支线黄门，可回访、跨层留用，但不存在无限供给。

首层正式出生候选字段在 `floors[0].safe_start_candidates`；根 `variant_spawn_candidates` 为父级接口的兼容 alias，构建时强制两者相等。四个候选按 `(y,x)` 排序，均为空格、与默认出生点处于同一个不穿越对象的初始分量，且四邻没有敌人。运行时变体规范由独立模块控制，仅镜像和选择安全出生，不改变固定怪位之间的相对拓扑和资源数量。

## 资源预算与四条见证

角色从 260 HP / 24 ATK / 8 DEF 开始。每层固定获得攻击 +2、防御 +1、16金币、45生命和一把选择黄钥匙；这些物品的拾取次序由真实通路约束，45生命位于第一名巡卫之后。支线选择是攻击 +3，或防御 +2 / 生命 +20。两种房间都给10金币。首层石甲门卫是固定特例，其余敌人按构建时整数曲线展开成明确数值，运行时不缩放。

完整锻炉在1/4/7/10/13/18层，各自只有一次攻击 +4、一次防御 +3和两次生命 +160；费用随章节明确增加。19层补给站只有两次生命 +180。商店永不补货，无售卖/回购或刷怪。

| 见证 | 支线与购买风格 | 决策事件数 | 最终 HP / ATK / DEF | 最终金币 |
|---|---|---:|---|---:|
| blade | 所有攻击房、可选藏箱；完整属性购买 | 323 | 138 / 153 / 47 | 946 |
| bulwark | 所有护甲房，不打藏箱；完整属性购买 | 297 | 271 / 90 / 89 | 454 |
| balanced | 攻击/护甲交替，仅部分藏箱；完整属性购买 | 306 | 374 / 123 / 67 | 664 |
| frugal | 攻击房、不打藏箱；省略10层铸甲 | 281 | 27 / 153 / 44 | 572 |

四条路线都使用每座完整锻炉的两瓶生命补给，但19层补给站只买一瓶，保留第二瓶有限库存。明确的购物事件形如 `buy:f10_shop/ward`，不会用一个 `buy:ward` 依赖「当前碰巧在谁旁边」。阶段位置依靠跨层四向 BFS 导航，导航不能悄悄拾取不在见证中的资源。

`validated_routes` 有完整事件、每步独立深拷贝的资源账本和预期损失；`witness_routes` 是同事件/最终预算的精简索引。最终监守的不同预览代价来自同一公式，不因路线切换脚本：锋刃345、铸甲918、交替441、节制360。

目前有限来源的宽松各分量上界是 HP4325、ATK153、DEF89、金币2128、黄钥匙21、蓝钥匙7。这些上界忽略花费和黄门互斥，**不是一个角色可以同时达到的联合最大值**。对象有敌人68、门49、拾取键28、商店7、楼梯40；封印哨兵的999防御超过全内容攻击来源上界且不挡主路。

四条见证有胜利余量不代表任意策略可赢。提前打高损失藏箱、错过永久属性或耗尽补给仍可能形成合法资源败局。不得用补货、加钱或删掉失败样本去保证随机策略全胜；恢复/救济仍按独立规则评审。

## 回放证据边界

`tests/replay_witnesses.gd` 对每个事件进行资源中立 BFS，实际调用正式规则完成每个移动、转层、购物和战斗，比较 HP/ATK/DEF/gold/每种钥匙，逐场核对预览等于实扣。报告绑定引擎、数据、规则和测试脚本哈希，并记录真实导航、转层、战斗比较次数。任何不可达事件、额外拾取、库存不足、不可胜战斗、账本差异或没有最终胜利都应失败；不能为了让报告通过放宽数据值断言。

输出 JSON 内的 `validation_summary.production_rules_replay` 固定写「not-tested by this builder」，因为重新构建数据不是重新执行 Godot 回放。实际通过与否在对应运行报告中声明。浏览器、画面、输入、声音和数小时目标均需后续独立验收，此数据构建与headless报告不宣称已玩。
