# 潮痕信塔：原创首1–10层内容与预算

「阶塔 · 潮痕信塔」是可改的临时名。目标为50层，目前仅有**真实编写的1–10层canonical内容**；11–50层未制作，不存在重复空壳floor、指向第11层的可通楼梯或50层胜利对象。第10层是信台切片milestone，`slice_complete=true`，`core.won=false`，允许继续回访。

本文件配合[new content](data/content.json)、[manifest](data/manifest.json)、[构建预算](data/design-budget.json)及[构建器](tools/build_content.py)。不新增project.godot；运行根仍是原`game/project.godot`。旧三层、21层、原baseline与1,362例恢复证据不变。这里的Python检查是设计预算与合法路径规划，**不是Godot实际回放、视觉认可、浏览器或时长验收**。

## 原创表达与来源

塔外失去联络后，玩家沿旧入塔队留下的潮线与布结寻找消息。首十层的目标是向塔外发出一道信号，不提前编造第50层结局。岚绘缺损的旧图、缺角铜签、盐封档案、守灯人留下的清水与无焰信台构成一条可实际兑现的线索链。

所有地图、数值、中文对白、NPC名称和对象命名均为本项目新原创，按仓库MIT许可交付；没有复制ITWonder或其他魔塔地图、对白、数值表，没有新下载素材或插件。玩法参考仅到确定性资源解谜的思想层面，不声称复现尚未确认的TapTap／小米渠道规则。视觉资源若由展示层复用，须沿用其独立来源及许可清单；本构建器不下载或生成素材。

## NPC回访能兑现，且不能刷资源

| 交互对象／事件 | 条件 | 首次效果与后续边界 |
|---|---|---|
| `f01_mapper / ev_mapper_intro` | 未初见、未兑换 | 原创线索说明，设`met_mapper`；不发免费钥匙。若先找到铜签再兑换，已兑换后不再播放过时初见任务。 |
| `f03_copper / ev_copper` | `copper_found=false` | 设`copper_found=true`，物件事件完成后不再阻路；不会自动发蓝钥匙。 |
| `f01_mapper / ev_mapper_exchange` | 已找到、未兑换 | 蓝钥匙+1并设`copper_redeemed=true`；该分支在NPC event_ids中优先。once及flag共同约束，只能兑换一次。 |
| `f05_archive_door` | 蓝钥匙至少1 | 消耗1蓝钥匙，门永久打开；重复走过不扣第二次。 |
| `f05_archive / ev_archive` | 尚未读档案 | ATK+3、DEF+2、HP+45，设`archive_read`；不补门钥匙、不刷新库存。 |
| `f07_keeper / ev_keeper_supply` | 已读档案、尚未领取 | HP+60、金币+12，设`keeper_supplied`。未读档案时只能播放一次提示；已经领取后不再提示去找档案。 |
| `f10_signal / ev_signal` | `f10_guard`已清除 | 设`relay_lit`并完成切片milestone；游戏的50层最终胜利仍为false。 |

所有event `once=true`，effect只用已锁定的`set_flag / grant / grant_key`；condition只用`flag / cleared`，没有任意脚本、动态坐标effect或循环奖励。NPC本体不清除且相邻交互不移动玩家；event拾取移动进格，其完成ID放入`completed_events`，不冒充Base `cleared`对象。第7层无需先播放intro才能兑现，奖励分支优先匹配。

两条见证都真实规划了F3→F2→F1→兑换→F2→F3→F4的往返，不把NPC奖励直接加到新楼层预算，也不换seed。其他玩家可以先走更高层再回来，故事flag与库存一直保留。

## 确定性战斗与有限商店

首版只使用普通玩家先手战斗。设计计算为`hit=ATK-enemyDEF`；hit≤0不可胜，否则`rounds=ceil(enemyHP/hit)`、`damage=(rounds-1)*max(0,enemyATK-DEF)`；仅HP>damage才执行。runtime必须调用原BaseRules同一结算入口供预览与扣除，不读取Python规划公式作为权威。

21个固定敌对象中，20个在两条见证中战斗，另一个是F9封存像（HP999／ATK99／DEF999／金币0）。它超过整个切片资源包络的最高ATK75，确实不可穿透；其位置不是任何已命名资源／出口的必经割点。普通移动应拒绝战斗并保持状态，不能把它当作死后补给入口。

三店在F2／F5／F8，使用相同可读价格但各自独立库存：

| offer | 价格 | 收益 | 每店库存 |
|---|---:|---:|---:|
| edge 整修刀刃 | 48金 | ATK+6 | 1 |
| ward 加固护具 | 36金 | DEF+4 | 1 |
| flask 封存清水 | 24金 | HP+90 | 1 |

刃路到第一店时83金币，护具+清水花60，剩23；三种全买需要108，眼前不够。护路到第一店时51金币，刀刃花48，剩3。各自随后战斗与后续楼层会再取得金币，可以回访买尚有库存的商品；没有无限商店、怪物重生或自动补货。

## 数据契约、复现与后续实际验收

canonical路径为`res://fifty/data/content.json`，content_id=`stairkeep-fifty-slice/v1`、schema1。manifest单列50目标、10 authored、40 not_authored；两种模式必须显式选择，默认null。classic新局使用新runSeed并整体重置；practice恢复真实完整checkpoint，收益和消耗一起回退。模式行为由新runtime实现，内容不迁移原3／21存档，不携带旧token、库存或证据身份。

在`game/fifty/`下使用已装Python标准库：

```text
python -B tools/build_content.py
python -B tools/build_content.py --check
```

构建没有随机种子输入，输出固定bytes；`--check`只在内存重建并比较既有文件，不写内容。当前静态检查已通过：10图连通、门割点、资源非负、库存／金币合法、双向楼梯、NPC条件与once、两条BFS见证及同字节重建。实际runtime尚须验两路线逐事件、钥匙仅扣一次、回访／重复NPC不赠资源、每seed D4下全部空间引用、classic／practice完整状态边界、旧save拒绝和未制作楼层拒绝不变状态。

独立只读审查又核了10图去掉标签后在8种D4变换下互异（包括同为61格／4环的F5与F7），31项门／主敌割点、18条双向楼梯，以及4个安全出生候选。从每个出生点分别重放两条规划见证，共8次均得到上表预算。Base成功交互商店后会进入该格，因此经过`f05_shop`的合法走廊仍可用；这不执行购买或增加资源。此审查也没有运行引擎。
